Social Harness helps applications connect agents that act for different people
or organizations. The application defines the work they do together. The
daemon its participants share identifies each agent, carries its messages,
and applies that agent's message rules before sending or delivering them.

A scheduling application, for example, supplies the booking logic. Its agents
exchange requests with students' and professors' agents through Social Harness.
The application may ask participants to follow shared booking rules, while each
owner keeps control of the rules protecting their own agent.

## What the application supplies

An application decides who may use its service, what roles participants have,
and which domain actions they may perform. It authenticates its human users
when needed and decides which agent may act for each account or session.
Shared rules explain how its agents should cooperate. The application also
needs a policy for changing or ending access.

Those choices are application responsibilities. Social Harness currently
provides messaging and local policy mechanisms. A common application admission,
role and revocation protocol remains to be defined.

## From an application request to another agent

The application supplies a destination and a message. The daemon checks the
message against the sender's firewall, gives it the next position in its
conversation and stores it for every member. It then applies each recipient's
message rules and offers admitted content to that recipient's host.

The host runs the model and tools. The daemon keeps policy and conversation
state. OpenClaw and NanoClaw connect through native channels.
Other hosts can use the [MCP client](/guides/mcp-client), with
receiving behavior defined by the [delivery contract](/reference/spec/host/receiving).
The [architecture](/concepts/architecture) explains how the components fit
together.

A successful ordinary send means the daemon has ordered and stored the
message. Delivery to the host is a later handoff. The host controls when its agent
processes that message and whether it informs a human. A reply is another
message with its own checks and outcome.

## Joining and accepting shared rules

An agent exists once its owner signs in to the daemon. The daemon records
the agent's identifier, its name and a principal identifier. It knows the
owner only as an account at the identity provider and does not establish
which person or organization that account belongs to. The application must
establish the account-to-agent relationship it relies on. The
[identity contract](/reference/spec/identity/identity-and-attribution#agents)
defines these values precisely.

An application states how its members work together as
[norms](/reference/spec/norms/norms): each has a protocol that orders its acts
and a form for each performative.
The members of a conversation agree on a norm through ordinary messages before
a task, and each member's firewall checks every act of that task against the
conversation's history, refusing acts out of turn or with invalid fields. A
firewall reads only the norms its agent holds, and an agent can ask a peer
for a norm it lacks.

An agreement covers one task in one conversation and ends when that task
completes or a member cancels it. The daemon does not track application
membership.

## Ending access and investigating harm

An application can deny access to its own service. A participant can change
its own editable policy. Applications cannot yet issue revocations or norm
updates that participants' firewalls apply automatically. An agent keeps its
identifier and name, and changing a group's participants creates a different
conversation.

An institution is another agent with a particular role, such as investigating a
disputed booking. It can receive evidence a participant chooses to disclose and
return an attributed finding. Each application or participant decides how to
use that finding. Social Harness supplies each member's conversation
history, whose accuracy rests on the daemon. Disclosure, investigation and
sanction protocols remain future work.
