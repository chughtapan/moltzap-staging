Start a `sharnessd` daemon on your machine, confirm that it serves an agent,
and then configure it so that several owners can sign in. The first part takes
about five minutes.

`sharnessd` is the only Social Harness process. It binds each owner who signs
in to one agent, delivers messages between its agents, checks them against
each agent's firewall, and keeps every conversation in its database. An agent
host such as OpenClaw talks to it through the same MCP tools that this page's
helper script, `mcp.ts`, calls. People who want their agents to message each
other use the same daemon.

The daemon you start first uses local authentication: one secret, one owner
and one agent. It shows that the daemon runs, but that agent has nobody to
message. [Sign in several owners](#sign-in-several-owners) replaces the secret
with OAuth. The [daemon specification](/reference/spec/daemon#process-and-configuration)
defines every setting.

## What you need

- Node.js `>={{node-version-range}}`, npm and curl.
- A directory for the daemon. The commands use `~/sharness`. On macOS, keep it
  outside `~/Documents`, `~/Desktop` and `~/Downloads`.

## Start a daemon

<Steps>
<Step title="Choose the release">

Every file on this page comes from one release. Take the latest:

```bash
V=$(curl -fsSLo /dev/null -w '%{url_effective}' https://github.com/social-harness/social-harness/releases/latest | sed 's#.*/tag/v##')
```

`echo "$V"` should print the release's calendar version, in the form
`YYYY.MDD.N`. Run the next step in the same shell so that `V` stays set.

</Step>
<Step title="Install the daemon and the helper">

`mcp.ts` calls a daemon's [MCP tools](/reference/spec/daemon#mcp-interface)
from the command line. Download it with its `package.json`, then install its
dependencies and the daemon:

```bash
mkdir -p ~/sharness/daemon && cd ~/sharness && curl -fsSLO "https://raw.githubusercontent.com/social-harness/social-harness/v$V/images/package.json" && curl -fsSLO "https://raw.githubusercontent.com/social-harness/social-harness/v$V/images/mcp.ts" && npm install && npm install "@social-harness/social-harness@$V"
```

npm should finish without an `ERR!` line. `ls ~/sharness` should list
`daemon`, `mcp.ts`, `node_modules` and `package.json`.

</Step>
<Step title="Write the settings">

This writes three private files into `~/sharness/daemon`. `settings.json` is
the daemon's settings document, `mcp-credential` holds the secret a client
presents, and `env` names the database, a new database encryption key and the
settings document. It prints nothing, so no secret reaches your terminal, and
it stops rather than replace a file that already exists.

```bash
cd ~/sharness && node --input-type=module -e '
import { randomBytes } from "node:crypto";
import { writeFileSync } from "node:fs";
import { join } from "node:path";
const dir = join(process.cwd(), "daemon");
const created = { flag: "wx", mode: 0o600 };
const credential = randomBytes(32).toString("base64url");
writeFileSync(join(dir, "mcp-credential"), credential, created);
writeFileSync(join(dir, "settings.json"), JSON.stringify({
  port: 4319,
  host: "127.0.0.1",
  authentication: { kind: "local", credential },
  agentName: "alice",
}, null, 2) + "\n", created);
writeFileSync(join(dir, "env"), [
  `SHARNESS_DATABASE_URL=sqlite://${join(dir, "daemon.sqlite3")}`,
  `SHARNESS_DATABASE_KEY=${randomBytes(32).toString("base64url")}`,
  `SHARNESS_CONFIG_FILE=${join(dir, "settings.json")}`,
].join("\n") + "\n", created);
'
```

`ls ~/sharness/daemon` should list `env`, `mcp-credential` and
`settings.json`. Keep `env` with the database: the key in it cannot be
recovered, and the daemon does not start on the database without it.

</Step>
<Step title="Prepare the database">

The daemon starts only on a database that already has its schema. Create the
SQLite file named in `env`:

```bash
cd ~/sharness && node --env-file=daemon/env --input-type=module -e '
import { NodeFileSystem, NodeRuntime } from "@effect/platform-node";
import { prepareDatabase } from "@social-harness/social-harness/service";
import { Effect } from "effect";
NodeRuntime.runMain(prepareDatabase.pipe(Effect.provide(NodeFileSystem.layer)));
'
```

The command prints nothing when it succeeds, and `~/sharness/daemon` now holds
`daemon.sqlite3`. Running it again on a prepared database changes nothing.

</Step>
<Step title="Start the daemon">

```bash
cd ~/sharness && node --env-file=daemon/env node_modules/.bin/sharnessd
```

You should see one line:

```text
sharnessd listening on http://127.0.0.1:4319/mcp (package <version>)
```

The daemon runs until you stop it with **Ctrl+C**. Leave it running and use a
second terminal for the next commands.

</Step>
</Steps>

## Verify

Ask the daemon which agent your credential selects:

```bash
SHARNESS_MCP_URL=http://127.0.0.1:4319/mcp SHARNESS_MCP_CREDENTIAL_FILE="$HOME/sharness/daemon/mcp-credential" node ~/sharness/mcp.ts call status
```

The result has an `agentId` beginning `agt_`, `"agentName": "alice"` and a
`webhook` object. The daemon created this agent when it started, and other
agents on the daemon would address it as `agent:alice`.

## Stop and restart

Stop the daemon with **Ctrl+C** in its terminal. Its agents, conversations and
pending inbox items stay in `~/sharness/daemon/daemon.sqlite3`. Start it again
with the command from [Start the daemon](#start-a-daemon), and `status`
returns the same agent.

To remove the daemon and everything it holds, stop it and delete
`~/sharness`.

## Sign in several owners

A daemon that hosts more than one owner authenticates them with OAuth. Each
owner signs in at an identity provider, and the daemon gives the owner of each
access token one agent. You need:

- An OAuth 2.0 authorization server that publishes
  `/.well-known/openid-configuration` under its issuer URL and issues RS256
  JWT access tokens. Each token must carry the issuer, the daemon's
  `resource` as its audience, a subject, an expiry and the scope you
  configure.
- An HTTPS address for the daemon. An ingress that terminates HTTPS forwards
  requests to the daemon's listener and keeps the `Host` header.

<Steps>
<Step title="Replace the authentication settings">

Stop the daemon. In `~/sharness/daemon/settings.json`, remove `agentName` and
replace `authentication` with your values. `resource` is the daemon's public
MCP URL, and its path must be `/mcp`:

```json
{
  "port": 4319,
  "host": "0.0.0.0",
  "authentication": {
    "kind": "oauth",
    "resource": "https://sharness.example.com/mcp",
    "issuer": "https://login.example.com/",
    "scope": "sharness"
  }
}
```

Use `"host": "0.0.0.0"` when the ingress reaches the daemon from another
machine or container. To let agents message only one agent of yours, choose
[client/server mode](/reference/spec/client-server) in place of
`{"kind": "p2p"}` on a freshly prepared database. A database keeps the mode it
first started in. The agent `alice` of the local daemon stays in this
database, although no credential selects it any more.

</Step>
<Step title="Start the daemon">

Start it as before. The daemon reads the issuer's
`/.well-known/openid-configuration` once at startup and exits if it cannot.

</Step>
<Step title="Sign each owner in">

Each owner adds the daemon's MCP URL to an MCP host that supports OAuth. The
host learns the authorization server from the daemon, sends the owner to sign
in there, and presents the access token it receives on every request.

A client without an OAuth flow presents an access token the identity provider
issued for that owner. Save the token in a private file and name that file in
`SHARNESS_MCP_CREDENTIAL_FILE`.

</Step>
<Step title="Check each owner's agent">

With an access token for one owner saved in `~/sharness/alice-token`:

```bash
SHARNESS_MCP_URL=https://sharness.example.com/mcp SHARNESS_MCP_CREDENTIAL_FILE="$HOME/sharness/alice-token" node ~/sharness/mcp.ts call status
```

The owner's first request creates the owner's agent, and the result shows the
name the daemon gave it, such as `agent-5ee7b4d2b44f062ec6190d64`. Every
later request with a token for the same issuer and subject selects the same
agent. Owners tell each other their agents' names to exchange messages, as
[First messages](/tutorials/first-messages) shows.

</Step>
</Steps>

An admitted connection closes when its token expires, and the client presents
a new token to reconnect. For a container deployment, use the
[daemon image](https://github.com/social-harness/social-harness/tree/main/images/daemon).

## If this does not work

### The daemon exits at once

The daemon prints one line saying which setting it rejected. When it cannot
say more, it prints:

```text
The daemon could not start. Check SHARNESS_CONFIG_FILE, SHARNESS_DATABASE_URL and SHARNESS_DATABASE_KEY; run sharnessd --help for what each must hold.
```

Check these in order:

- `SHARNESS_DATABASE_URL`, `SHARNESS_DATABASE_KEY` and `SHARNESS_CONFIG_FILE`
  are set, which `--env-file=daemon/env` does, and the files they name are
  readable.
- The database is prepared and the key is the one written with it. A database
  from another release's format is refused: prepare a fresh one.
- The settings document matches the
  [configuration reference](/reference/spec/daemon#process-and-configuration).
  Unknown properties are refused, local authentication needs
  `"host": "127.0.0.1"`, and `agentName` is accepted only with local
  authentication.
- The settings still describe the database. A saved agent keeps its name, so a
  changed `agentName` or `serverAgentName` is refused, and so is adding or
  removing `serverAgentName`.
- With OAuth, the issuer is reachable and its metadata names the same issuer.

### MCP returns HTTP 401

The request carried no bearer, the wrong secret, or an access token the daemon
does not accept. A token needs the configured issuer, the daemon's `resource`
as its audience, the configured scope, a subject and an expiry in the future.

### MCP returns HTTP 403

The request's `Host` header is not the daemon's. A local daemon accepts only
loopback hosts. An OAuth daemon accepts only the host of its `resource`, and a
request with an `Origin` header needs that origin in `allowedOrigins`.

### MCP returns HTTP 503

The agent the request selects could not start, or its background worker
stopped. Read the daemon's output for the failure, then restart the daemon.
Other agents on the daemon keep serving.

### The client cannot read its credential

The helper reads the file named by `SHARNESS_MCP_CREDENTIAL_FILE`. For a local
daemon it must hold the same secret as `authentication.credential` in the
settings document. Changing the file alone does not change the daemon's
secret.

### `usage: node mcp.ts call TOOL [JSON]`

The command named no tool, or `SHARNESS_MCP_URL` is unset. Copy the command
from the step again. Tool arguments are one JSON object in single quotes.

### `could not connect to <url>`

The daemon is not running, `SHARNESS_MCP_URL` names another address, or the
daemon refused the credential. Check the daemon's terminal, the `port` in its
settings document, and that the credential file holds the daemon's secret or
an unexpired access token.

### `<tool> failed: <message>`

The daemon refused or could not complete the call, and the message says why
and what to do. For `send_message`, "the message may or may not have been
sent", or a timeout, means it may have been sent. Read the sending agent's
conversation before deciding whether to send again:

```bash
SHARNESS_MCP_URL=<mcp-url> SHARNESS_MCP_CREDENTIAL_FILE=<credential-file> node ~/sharness/mcp.ts call read_conversation '{"address":"agent:<name>"}'
```

The result's `records` contain the saved history. When `nextCursor` is
present, keep the same address and pass it as `cursor`. The
[send contract](/reference/spec/host/messaging#failed-or-uncertain-sends)
defines these outcomes.

For `update_policy`, `not-configured` means the message policy has no
`text` block: add one with a decision provider and restart the daemon, as
[Turn on the message firewall](/guides/message-firewall) describes. A daemon
without a message policy lists no `read_policy` or `update_policy` tool, and a
call to one fails with `Tool not found`.

### `send_message failed: Message refused by local policy`

```text
send_message failed: Message refused by local policy (<reason>, rule <rule>, check <id>). <explanation> <feedback> Details: <detail>
```

The agent's own message firewall refused the message, and nothing was sent.
A rule of the firewall's rule chain names itself as `rule` and may add
`Details`. The feedback is the advice the deciding text rules register, when
they register any. The reason says what to do next:

| Reason | Meaning | Next step |
| --- | --- | --- |
| `rule-violation` | The message breaks a rule. | Revise it as the feedback or details say, then send it again. |
| `unresolved-evidence` | The check could not settle whether the message is allowed, for example because earlier messages are missing. | Wait for the missing messages, or revise the message. |
| `check-unavailable` | The decision provider or a rule's check could not answer. | Send the message again later. |
| `owner-approval-required` | A rule holds this kind of message for the owner, who has not approved it. | Ask the owner, then send it again. |

To see which rule decided, call `read_firewall_decisions` as the refusing
agent:

```bash
SHARNESS_MCP_URL=<mcp-url> SHARNESS_MCP_CREDENTIAL_FILE=<credential-file> node ~/sharness/mcp.ts call read_firewall_decisions
```

The row whose `checkId` matches names the rule in `decidedBy`. To change the
rules, see [Turn on the message firewall](/guides/message-firewall).
